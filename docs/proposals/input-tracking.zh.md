# 输入处理跟踪提案

> [English](input-tracking.md) | 中文

状态：已通过 [PR #538](https://github.com/juex-ai/juex/pull/538) 实现。更新：2026-09-08。下文保留设计讨论；已交付行为、限制和升级要求以 [输入跟踪模块](../../internal/features/inputtracking/README.zh.md) 为准。

建议在现有输入机制上增加一个简单的持久化勾选清单：框架自动登记，recitation 自动展示未勾选输入，模型处理后调用工具勾选。本文是设计建议，不替代当前 DOMAIN 与 ARCHITECTURE。

## 1. 首版只增加一个勾选标记

每条需要跟踪的输入只有两种情况：

- **未勾选**：仍需模型关注，可能尚未开始、部分完成、暂时受阻，或包含仍有效的约束。
- **已勾选**：这条输入已处理妥当，无需继续提醒。

用可空的 `checked_at` 表达即可：为空表示未勾选，由框架在工具提交成功时写入时间。模型不维护时间戳，也不选择处理状态、失败类别或处置类型。

原有输入 ID、原文、来源、执行尝试和错误记录继续使用。跟踪资格是框架接收输入时的元数据；未启用跟踪与“未勾选”不能混淆。

不新增 open/blocked/resolved、completed/incorporated/superseded/cancelled 等状态集合，不新增进展字段、证据字段或输入之间的关系图。进展继续通过对话、Goal、Notes 和现有工具结果表达。

## 2. 和 pending_input、模块的关系

现有 `pending_input` 负责可靠接收、排队、注入、执行尝试与失败恢复。新增清单只回答“这条输入是否还需要提醒模型”，复用同一个 `input_id` 和原始输入。

| 部分 | 职责 |
| --- | --- |
| Runtime / Framework | 自动登记、输入存储、勾选提交、当前集合保留、执行恢复与生命周期边界。 |
| `input-tracking` 模块 | 一个勾选工具、每次请求的 recitation，以及轻量的勾选状态展示。 |
| Goal / Notes | 继续分别表达长期目标和工作笔记，不承担逐条输入登记。 |

保持此前的模块建议：standard 默认开启、minimal 默认关闭，仍待评审。关闭模块不影响原有消息投递；不注册勾选工具、不注入清单、不跟踪新输入。旧未勾选记录保留，重新开启后在下一次正常执行时恢复展示，不自动回填关闭期间的历史或启动旧工作。

当前状态存储仍由 Runtime 统一拥有，采用已确认的 `inputs.json` 命名，表示原 `pending_inputs.json` 同时容纳尚待执行和尚待勾选的输入。这里不复制原文到另一份 Notes 文件，也不重建一套投递状态机。

Framework 的接收、排队顺序、step 边界注入和恢复语义保持原样。`pending_count` 按实际待投递队列计算，不按 `inputs.json` 的记录数计算。勾选成功即退出 recitation；文件记录还需等执行恢复不再依赖它时才能删除，勾选不会取消正在执行的 Turn。

现有内部 `processed` 表示输入已写入历史，不等于模型勾选。因此新增标记使用 `checked_at`，不复用它的含义。

首版范围仍是模块开启期间接受的直接用户对话输入，包括空闲时的第一条消息、执行中追加的消息和用户直接发给 Worker 的消息。根据可信接入元数据识别来源；系统 continuation、Tool 结果、Observation、MCP Notification 和 Worker 自动通知不自动进入勾选清单。

## 3. 只提供一个模型工具

建议名称：`check_inputs`，只接受要勾选的输入 ID，可以一次勾选多条：

```json
{"input_ids": ["I101", "I103"]}
```

不提供 `get_inputs` 或通用 `update_inputs`。模型已从 recitation 获得当前未勾选输入，不需要再调用查询工具；也无需为了勾选填写状态、修订号、理由、进展或结果引用。

工具只允许勾选当前 Thread、当前工作范围内已交付模型的跟踪输入，不能创建、编辑、删除输入，也不能提前勾选尚未交付的消息。重复勾选同一输入幂等成功；不存在或越界的 ID 明确失败。一批 ID 先统一校验，再原子提交，避免部分成功难以判断。

工具返回本次确认的 ID。勾选事实的时间、Turn 和调用关联由框架自动记录，不增加模型参数。

首版不提供取消勾选工具。用户指出漏做或错误时，新消息会成为新的未勾选输入，原勾选历史保留。

## 4. 什么时候可以勾选

勾选表示处理妥当，不等同于“模型已经看过消息”，也不要求每条消息都变成独立任务。

| 输入场景 | 规则 |
| --- | --- |
| “实现导出并写测试” | 实现和测试都完成后再勾选，不能完成一半就清掉整条。 |
| “现在进度如何” | 回答后可以勾选这条；原来的实现任务仍保持未勾选。 |
| “格式改为 JSON” | 按修正后的要求工作，实际落实后再勾选；不能只说收到就勾选。 |
| “这次不要合并 PR” | 适用工作结束前保持未勾选，让约束持续出现在 recitation。 |
| 工作失败或等待用户 | 保持未勾选，通过现有对话说明错误或阻碍。 |
| 用户明确取消或完全替代旧要求 | 模型处理该指令后，可以勾选已无需执行的旧输入；不增加 cancelled 或 superseded 类型。 |

原文保持不变，按时间顺序呈现。提示词明确要求以后续用户修正为准，不机械执行已经撤销的旧表述；不能为了清空列表自行取消要求。部分修正不等于整个原任务已经处理妥当。

框架校验身份、范围和提交顺序；是否处理妥当仍由模型判断。首版不增加强制证据参数或独立验证模型，不能声称勾选证明了结果正确。

纯问答必须先保存回答，再提交勾选。若同一次模型响应包含回答和工具调用，框架保证回答先持久化；不能先勾选，再依赖尚未生成的回答。若必须另用一个步骤勾选，接受这一短调用成本。

## 5. recitation 提供完整的未勾选信息

每次 Provider 请求自动展示当前范围内所有已交付、未勾选输入的 ID 与内容。原始排队机制仍负责尚未交付的消息；它们不提前出现在可勾选清单中。

```text
以下输入仍未勾选。保留原有工作，并结合后续修正处理。
处理妥当后调用 check_inputs；未勾选不表示此前没有做过工作。

[I101] 实现导出功能，并写测试。
[I104] 这次不要合并 PR。
[I105] 增加异常输入的测试。
```

正文复用原始消息或现有输入投影，不再生成一份可能漏掉要求的语义摘要。附件和大内容沿用现有媒体、spool 和工具回读机制；本模块不增加查询协议。

因为没有查询工具，首版不做需要模型翻页才能发现输入的清单。必须显式计入 recitation 的上下文预算；优先使用既有 compact/内容投影机制，仍然容纳不下时报告容量问题，不能静默隐藏未勾选 ID 或要求。

已勾选输入不再作为待办反复注入，原文和勾选事实仍保留在历史中，compact 摘要需尊重已勾选事实。recitation 每次从持久状态重建，不把每次快照追加为新的用户消息，也不提升原始内容的指令权限。

首版不自动判断哪些历史完成项值得重新展示，也不维护单独的“有效约束”状态；需要持续提醒的约束保持未勾选即可。

## 6. 持久化与恢复必须保留的规则

1. **接受时登记。** 在同一次持久接受提交中保存输入及需要时的空勾选标记，成功后才确认接受。不能依赖模型写 Notes 或事后的异步回调补建清单。
2. **出队不等于勾选。** Turn 正常结束、API 请求成功或失败、compact 都不能自动写入 `checked_at`。原有执行结算继续进行；未勾选记录独立保留。
3. **勾选先提交再发布。** 沿用 Generation 事实先持久提交、当前状态更新后发布的顺序。已提交勾选与当前文件之间的崩溃窗口按 ID 对账，不重复执行工具。
4. **提醒不等于重新入队。** 已投递但未勾选的输入由 recitation 提醒，不自动当成新用户消息重放。执行恢复沿用已有策略；已完成工具的结果直接恢复，未知结果不盲目重试。
5. **保留有界。** 当前集合保留仍需投递/执行恢复的输入以及当前范围的未勾选输入。超过容量在接受前拒绝；投递 TTL 不得静默抹掉已接受的未勾选要求。已勾选且不再参与执行恢复的记录可以移出当前集合，历史保留。

普通停止、Provider 重试耗尽和模块关闭都保留未勾选记录，服从原有暂停和恢复控制。进程重启不额外启动另一套 continuation。

宿主 `/new` 明确结束旧清单的活动范围，保留历史，不把旧未勾选输入伪装成已勾选；边界后接受的输入属于新范围。compact 保持同一工作范围。模型 `context_new` 不能隐式清理仍有未勾选项的清单，应使用 compact。

存储调整遵循项目 clean break 原则，不增加旧格式别名、双读或自动迁移；实施前核对旧未完成输入并安排人工交接。本提案不执行存储切换或删除现有数据。

## 7. 首版不增加独立的自动续跑门禁

二态清单无法自动区分“被遗漏的任务”“等待用户的任务”和“仍然适用的约束”。因此，未勾选项存在时不无条件阻止 Turn 结束，也不以此启动无限 continuation。

每次请求通过 recitation 提醒模型处理；已有 Goal continuation 继续按自己的规则工作。移除前版独立 FinishPolicy、三次无进展检测及 Goal/输入续跑仲裁的设计。

这个取舍意味着：首版确保未处理信息不会随出队或 compact 静默消失，但不保证模型会立即完成所有输入。如果评估显示模型仍频繁带着可执行事项结束，再单独讨论结束检查，不为此提前增加 blocked 等状态和工具。

## 8. 展示、验证与调研依据

Web 可在输入旁显示一个已勾选标记，执行失败仍由已有错误展示表达；助手正文保持普通对话文本。不增加任务看板、分类处置入口或新的语义完成等待模式。`send --wait` 继续表示消费输入的 Turn 已结算。

实施验收重点：第一条和运行中输入均自动登记；多输入分别勾选；原文不可改；勾选幂等且不越界；失败与 compact 不清账；回答先于勾选持久化；进程恢复不重放已有操作；模块关闭/重新开启及工作范围切换正确；大清单不静默漏项。跨模块行为需要 e2e，可见 Web 变化需要浏览器验证，遵循[本地验证技能](../../.agents/skills/juex-localtest/SKILL.zh.md)。

模型评估复现最初五类场景，比较现有机制、Notes 提醒和本提案，报告漏项、重复执行、错误勾选、恢复后未勾选输入保留率及额外调用/token。不预先承诺改善幅度，尤其检查模型是否仍会提前结束。
